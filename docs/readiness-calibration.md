# 校准综合准备度

综合准备度（0–10，算法见 [health-methods.md](health-methods.md) 第 7 节）的默认权重是工程估计，没有用任何人的数据校准过。这里的做法是：每天手动记两样东西，记满 3 周后，用一个脚本把它们和算出的准备度做对比，给出调整权重的建议。**脚本只打印建议，不会修改任何配置**，要不要改由你决定。

## 每天记什么

| 项目 | 取值 | 上传的 `type` |
| --- | --- | --- |
| 苹果「健身」App 里的准备指数 | 0–10，可以有小数 | `apple_fitness_readiness` |
| 自己的体感 | 1–5 的整数：1 很累，3 一般，5 状态很好 | `perceived_readiness` |

两样可以只记一样。同一天记了几次，后端只用**时间最晚**的那一次，所以记错了重新记一次就行。最好每天在差不多的时间记（例如起床后），和准备度用的是同一晚的数据。

### 在 App 里记

iPhone 或 Mac App 的「健康」页有「今天的记录」：选日期（默认今天，也可以补记前几天），填健身 App 的准备指数、选体感，点「保存」。保存后 App 会请 Mac 立刻读取，几秒后「今日准备度」卡片上会出现「你记的健身 App 7.5 · 体感 4」。

补记前几天时，App 把记录的时间写成「那一天 + 现在的时刻」，所以后端会把它算到那一天，而且比那一天之前的记录晚，会替换掉之前的。

### 用快捷指令记

适合每天早上点一下就记好。先在 Mac 上给快捷指令建一个只能上传健康数据的令牌（见 [api.md](api.md)「连接与鉴权」）：

```bash
cd backend
uv run python -m scripts.tokens create 快捷指令 --scope health_upload
```

然后在 iPhone 的「快捷指令」App 里新建一个快捷指令：

1. 「要求输入」：提示「健身 App 的准备指数」，类型选「数字」。
2. 「从菜单中选取」：1、2、3、4、5（体感）。
3. 「当前日期」，再用「格式化日期」设成 ISO 8601（包括时间）。
4. 「获取 URL 内容」：
   - URL：`https://<机器名>.<tailnet 名>.ts.net/api/v1/health/samples`
   - 方法：POST；头部：`Authorization` = `Bearer <上面创建的令牌>`
   - 请求体 JSON：`samples` 是一个数组，两项分别是：
     - `{"id": "apple-<格式化的日期>", "type": "apple_fitness_readiness", "value": <第 1 步的数字>, "unit": "", "start_at": <格式化的日期>, "end_at": <格式化的日期>, "source": "快捷指令"}`
     - `{"id": "feel-<格式化的日期>", "type": "perceived_readiness", "value": <第 2 步选的数>, "unit": "", "start_at": <格式化的日期>, "end_at": <格式化的日期>, "source": "快捷指令"}`

`id` 要每次不同（上面用时间拼出来），重复的 `id` 会被当作重复上传忽略。返回 `{"accepted": 2, ...}` 就成功了。快捷指令上传的数据最多 15 分钟后进入汇总（健康插件每 15 分钟读取一次新上传）。

超出范围的值（准备指数不在 0–10、体感不是 1–5 的整数）会被丢弃，不会猜测。

## 运行校准脚本

在 Mac 的 `backend` 目录：

```bash
uv run python -m scripts.readiness_calibration                       # 默认最近 60 天，和两项的平均比
uv run python -m scripts.readiness_calibration --target apple         # 只和健身 App 比
uv run python -m scripts.readiness_calibration --target perceived     # 只和体感比
uv run python -m scripts.readiness_calibration --days 90 --json       # 更长的窗口，输出 JSON
```

今天不计入（今天还没过完）。可用的日子少于 21 天（`--min-days` 可改）时，脚本只告诉你还差几天。

### 怎么读结果

- **一致程度**：算出的准备度和你的记录之间的秩相关（-1 到 1）。越接近 1，说明你觉得状态好的日子，算出的分数也高。还列出四项各自和记录的秩相关，可以看出哪一项和你的感觉最一致。
- **平均差**：算出的分数平均比你的记录高或低多少。权重只改变四项之间的比例，改不了这个整体偏差；偏差大时可以考虑调整第 7 节里各项的换算参数（如睡眠目标时长），这一点脚本不做建议。
- **当前权重 / 拟合权重的平均误差**：拟合权重是在 0.05 的网格上搜出来的、让算出的分数最接近记录的一组权重（四个权重加起来是 1；和实际打分用同样的规则：只在当天有分数的项目上归一化，少于 2 项不打分）。
- **留一法误差**：只有三四周的数据时，拟合很容易「背下」这几周的偶然波动。留一法每次拿掉一天、用其余日子拟合、再预测拿掉的那一天，得到的误差更接近换权重后在以后的日子里的真实效果。
- **建议**：只有留一法误差比当前权重的误差低至少 10% 时，才建议换成拟合权重，并打印一段可以并进配置的 JSON；否则建议保持当前权重。

### 采用建议

脚本不会改配置。要采用时，把它打印的 `{"readiness": {"weights": {...}}}` 并进 health 插件的配置，用 `PATCH /api/v1/plugins/health` 提交。注意 `config` 是整体替换的，要带上已有的其他设置。改完立即生效，不需要重算历史数据。可以过几周再运行一次，看看误差是不是真的变小了。

## 局限

- 健身 App 的准备指数本身也是 Apple 的模型算出来的，它和我们的分数一致，不代表两者都对；体感是主观的，也会受心情影响。两者都只是参照。
- 三周的数据很少，相关系数和拟合权重都有很大的偶然性；留一法和 10% 的门槛只能减少、不能消除过拟合。
- 某一项（例如训练负荷）在这段时间几乎没有变化时，数据里看不出它的作用，拟合可能把它的权重压到 0；这不代表它不重要。

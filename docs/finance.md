# 记账 Bot「记账」

`finance` 是默认停用的本地记账插件。启用后，贴图 `carlotta` 对应角色「记账」，人设和角色笔记仍在 `Bots/记账/`；账单及月报在**没有任何读者**的私人知识库主题中。金额计算、类别、去重、退款、生活费和报销全部由代码完成；模型只拿月报汇总写一段解读。

## 每月导出和上传

下面是按常见 App 入口写的操作指引，未在本轮登录真实支付或银行 App 验证；菜单名称以用户当前版本为准。选择涵盖整个生活费周期的日期范围，保留平台原始文件，不用 Excel 重新保存后再导入。

1. 微信：在「我 → 服务 → 钱包 → 账单」找「常见问题 / 下载账单」，用途选**用于个人对账**，设置日期并发送到自己的邮箱。从邮件保存 CSV、XLSX 或 ZIP。若平台要求验证，只在微信自己的 App 中完成，不告诉 Bot 支付密码。
2. 支付宝：打开「我的 → 账单」，在更多或帮助中找「开具交易流水证明 / 下载账单」，选择**用于个人对账**，设置日期和自己的接收邮箱，下载原始明细或 ZIP。本插件需要交易时间、分类、对方、商品说明、收支、金额、付款方式、交易状态和交易订单号，余额收支明细或商家对账单不是同一格式。支付宝[服务中心](https://cschannel.alipay.com/mobile/helpDetail.htm?help_id=201603346502)另有余额明细下载说明，不能据此断言个人对账导出列完全相同。
3. 招商银行：在招商银行 App 搜索「交易流水 / 打印交易流水」，选对应借记卡和日期，导出带**记账日期、货币、交易金额、联机余额、交易摘要、对手信息**的流水 PDF。这里只读用户已导出的文件，不登录银行；信用卡账单、图片截图和企业流水暂不支持。PDF 版式尚未用真实样本核对，不能解析时保留原件。
4. App 知识库页选「财务」主题上传，或在 Mac 将文件放到 `知识库/财务/` **最外层**。`说明.md` 和所有子文件夹不扫描。CSV、XLSX、ZIP 只能上传至无读者主题；PDF 按现有上传规则接收。App 上传最多 50 MiB，本机 PDF 上限沿用 500 MiB，截断的提取文字拒绝导入。
5. 等最多 5 分钟，或对记账说「现在导入账单」。认不出、解析失败、缺密码的文件之后不再每 5 分钟重读，文件内容变了或你说「现在导入账单」时才重试。需要 ZIP 密码时，在记账对话里说文件名与**压缩包解压密码**，由 `finance_unlock` 一次使用。AES 等不支持的加密会显示 `needs_unzip`：请在本机解压，再上传里面的文件。

不读取邮箱，不自动下载账单，不获取实时微信、支付宝或银行卡交易提醒；用户每月补传。没有导入的日期不能当作没有消费。

## 私人主题、归档和失败

配置 `topic` 默认「财务」。不存在时用 `Knowledge.topic(readers=[])` 创建；已存在时绝不清空用户的读者设置。只要主题有读者，插件状态和卡片显示「财务主题必须没有读者」，doctor 不通过，拒绝导入与账本访问。每次操作都会重新检查读者；不要给财务主题勾选任何 Bot 或 Agent，记账通过专用工具访问账本。

成功后原文件移动到 `账单原件/<微信|支付宝|招商银行>/<覆盖结束年>/<原文件名>`。采用 `safe_path` 检查路径，拒绝文件及祖先目录符号链接，以同盘硬链接发布后再移除收件箱文件名；同名加 ` (2)`、` (3)`，不会覆盖已有文件。sha256 相同的再次上传不重复记账，仍归档并显示「重复的账单，已归档」。SQLite 提交先于归档：归档失败留在原地，下次只重试归档，不重复记账。

无法识别、解析失败、缺密码或不支持加密均留在原地。卡片理由为固定文案，日志、runs、错误分类不含金额、商户或转账对象。需要核对时保留原件，不通过文件名猜来源。归档状态在 `finance_files`，成功导入的 SHA、来源、起止日期、行数和归档路径在 `finance_imports`；账本表为 `finance_transactions`。插件删除或停用不删除这些历史数据。

ZIP 仅在数据目录 `finance/tmp/` 的临时目录解出账单，完成或失败后清理；不使用 extractall，不跟随链接，不解出任意成员路径。限制 100 个成员、解压总量 50 MiB；同一 ZIP 包含多个账单时必须同一来源，一起成功才提交。只使用 Python 标准库，不安装依赖。已核对 [bsdtar 官方手册](https://github.com/libarchive/libarchive/blob/master/tar/bsdtar.1)和[读取源码](https://github.com/libarchive/libarchive/blob/master/tar/read.c)：没有找到可用的口令文件/环境变量接口，`--passphrase` 会暴露命令行参数，因此未启用外部解压回退。

## 周期和统计口径

- 周期从配置的生活费日到下次生活费日前一天，默认每月 1 日；31 日遇短月取该月末日，跨年同样计算。剩余天数含今天。
- 招商银行转入在生活费日前后 3 天内，且不少于设置金额的 80%，识别为 `allowance`；`family` 非空时还必须匹配对方。提前到账归最近的生活费日所在周期。周期预算为识别到的生活费合计；没有时用设置金额并写「按设置的 2000.00 元算」。家人名单为空时仅靠日期和金额，可能误认其他大额转入，可在对话里更正类型。
- `period=year` 汇总本自然年的消费和额外收入；预算合计本年已开始的生活费周期，缺失周期逐期用设置金额，不预测全年每天可花。
- 花销是 `spend` 抵掉匹配退款，不含在家时的 `ask`、`yes` / `reimbursed` 报销（包括 `family_pays` 匹配的家里报销项）、大件和 `linked_id` 指向另一笔的重复项。在家时的花销默认算家里的，用户说哪笔家里不报（`no`）才算进花销；`finance_summary` 另给它们的合计 `ask_cents`。外卖（吃饭类里对方或商品含「外卖」「饿了么」「美团」的）另给 `takeout_cents` 和笔数 `takeout_count`，已在吃饭里，不重复计。剩余 = 预算 − 已花；每天可花 = 剩余 ÷ 含今天的剩余天数。可以为负数。
- 用自己积蓄买的大件（手机、手表这类）由用户告诉记账，她用 `finance_big` 标记（可带名称，如「手表」）。大件花的是自己的钱，但不是生活开销：不算进周期的已花和类别，`finance_summary` 单独给 `big_cents`，卡片「今年的大件」逐笔列出，月报单列一行。big=false 放回生活费。不按金额自动认定，上千的自费支出记账会问一句。
- 微信红包、配置关键词（默认「分红」）对应的转入为 `extra_income`；手动也可记，红包与分红等分开汇总，**不加入生活费预算**。其他转入为 `income`，卡片提示待确认，不加入预算或额外收入。
- 跨来源按同额、日期差不超过 2 天、平台付款方式含招商/招行、银行摘要或对手含支付宝/财付通/微信匹配；银行项指向平台项，保留平台商户信息。自己的零钱充值/提现、零钱通、余额宝转入转出是 `transfer`。没有可确认的平台配对时，不单凭「支付宝」等字样把银行支出当作自己的转账。
- 退款优先用原单号或商户订单号；没有明确单号匹配时用 30 天内同对方、同金额且候选唯一的支出。退款抵回**原支出的周期**，不把当月退回的往月款项当收入增加预算，抵扣最多到原金额。全额退款状态使原支出净额为零，不再重复扣退款。未匹配退款保留明细，暂不抵账。
- 同额且时间差不超过 24 小时、候选唯一的手动支出与导入项合并，导入项保留，手动类别、备注和用户已作出的报销决定带过去；明细工具及卡片不展示隐藏项。单号按 `(source, source_id)` 幂等；重复的聊天记账请沿用 `request_id`（消息 ID；一句话记几笔时依次加 `:1`、`:2`）。有歧义时保留多笔供人工核对，不擅自合并。
- 默认类别为吃饭、交通、购物、娱乐、会员订阅、学习、通讯、医疗、其他。优先级为记住的对方规则、配置关键词、内置关键词。`finance_categorize(remember=true)` 回填同对方历史，不调用模型分类。
- 每个来源显示截至日期，取导入覆盖结束日与最晚交易日较大者；没有识别到导出期间时注明「仅按最晚交易日，未确认完整覆盖」。截至某日不保证中间没有缺口。月报会保留这些说明。

## 现有资产

卡片「现有资产」是各账户最近一次知道的余额加起来，标出截至哪天；之后的收支不在里面，所以不是实时余额。

- 招商银行流水每行都有余额。导入（或 `finance_reread` 重读）时，每张卡最后一行的余额记成这张卡在账单截止日的余额，账户名如「招商银行(1234)」。
- 微信账单没有零钱余额，支付宝余额、现金也一样：用户告诉记账（「微信零钱现在 256.40」），她用 `finance_balance` 记下，日期默认今天。同一天流水和用户都给了，用用户说的。
- 招行 App 首页显示的是所有卡的总资产，记成「招商银行」。它代表这家银行的全部卡，直到有更新的流水给出各卡余额，那时改为逐卡列出。
- `finance_summary` 只给合计（`assets_cents`）和最早的截至日（`assets_as_of`），不给账户名，因为账户名里有卡号后四位。逐个账户只有记账能看。
- 有余额超过一个月没更新，卡片提醒跟记账说一声现在的。

## 在家时的报销

在家时花的钱家里会报销。哪几天在家由用户告诉记账（「10 月 1 号到 7 号在家」「这周末回去了」），她用 `finance_home` 记下起止日期；这几天的支出标 `ask`，其他时间是 `no`。会员订阅是自动续费，哪天扣都是自己的，不标 ask。拿掉一段（remove=true）或新加一段，都会重新判断用户还没表态的支出，已经确认过的不变。`finance_summary` 返回这些日子（`home_periods`）。

不是每个周末都回家（比如军训的一个月只回了一次），所以默认不把周末当成在家。真的每周都回时，打开 `every_weekend_at_home`，周五 17:00 到周日 24:00（`home_from` / `home_until`，可改）也算在家。

`family_pays` 里的关键词（如 AI 会员和 API：`claude`、`chatgpt`、`deepseek`，或经苹果扣款的 `apple.com/bill`）出现在对方或商品里的支出，不论哪天，都算家里报销：标 `yes`，不进生活费花销，也不进周日的在家提醒。同一渠道里家里不报的（经苹果充的游戏），用户说了以后用 `finance_reimburse` 记 `no`，再按需改类别；用户的决定不会被规则改回。一笔扣款里只有一部分是用户自己的（苹果把会员和游戏充值合成一笔扣），用 `finance_split` 拆出那部分：它成为单独一笔（来源 `split`），是用户自己的、用给定的类别，算进生活费；原扣款只按剩下的金额算，报销状态不变。再拆一次替换那部分，金额 0 合回去。改了关键词，重新加载插件时会重新判断用户还没表态的支出（已报回来的不变），并立刻重新对一遍已有的转入。

周日 21:00 的 `reimburse_check` 查所有新出现、尚未提醒的 ask，包括本月补导入的往周支出。摘要只写笔数和合计（摘要也会进每日文件夹的 今天.md，所有 Bot 都能读），告诉用户这些算家里的、不占生活费，家里没报的跟记账说是哪几笔；App 页面上不逐笔列出（交易 ID 只给 Agent，用 finance_transactions 查）。同一笔不重复提醒。`finance_reimburse` 记 yes/no；no 放回生活费花销，用户说「报销到了」后 `finance_reimbursed` 标 reimbursed，可指定 IDs 和金额。

按周末自动判断时，只有当前和上一个生活费周期里的周末支出会标 ask：第一次导入几个月的旧账单时，不会把过去每个周末都拿来问。用户说出的日子不受这个限制。

招商银行或微信出现与 14 天内 yes 支出净额合计相差不超过 1 元的转入时，自动标为 reimbursement（已识别为生活费的转入从不参与；配了 `family` 时只认名单里的转入），同时将支出标 reimbursed。家里有时用微信红包报销：名单里的家人发来的红包同样参与匹配（要求配了 `family`），对上的不算额外收入。合计对不上时，再看 3 天内单独一笔 `family_pays` 支出：到账金额不少于它、且不超过它向上取整到 10 元（45 元报回 50 元），就认最近的那一笔。这是规则匹配，尚不能确定付款人实际用途；分笔到账、超出时限和不等额到账请人工指定 IDs 确认，报销用的红包没对上时用 `finance_categorize` 把它改成 `reimbursement`。本插件不发送报销消息，不转账。

## 工具权限

所有 `finance_*` 工具由已启用插件注册。`reader=记账, kind=bot` 的角色对话、MAIN 和旧的无 reader / kind 令牌可以用全部工具。显示名 `bot_name` 无法冒充角色；Agent reader 同名也不获得明细权限。其他 Bot 只能调用 `finance_summary`，明细、解锁、写入、月报工具均拒绝并返回「只有记账能看明细」。内部月报运行另有临时 `finance_report` 身份，仅允许汇总及本次周期的 report_input/write，不允许明细工具或私人文件读取。

| 工具 | arguments |
| --- | --- |
| finance_summary | `period`: cycle / previous / year；返回整分、类别合计、报销、额外收入、覆盖，无商户或对方 |
| finance_transactions | 可选 start/end 日期、source、direction、kind、category、reimburse、big；limit 1–50，默认 20 |
| finance_add | amount（元）、category?、note?、occurred_at?、direction?、kind?、counterpart?、item?、request_id?；收入方向 in，红包/分红 kind=extra_income |
| finance_categorize | id、category、remember（默认 true）；或 id、kind 修正转入类型（income / extra_income / allowance / reimbursement / transfer），两种修改分开调用 |
| finance_reimburse | ids 数组或 all_ask；decision=yes/no |
| finance_reimbursed | ids?、amount?；未给 IDs 取全部 yes，金额需匹配净额，部分到账请选 IDs |
| finance_big | id、big（默认 true）、note?（它是什么，1–100 字）；记成或取消大件，只能是支出 |
| finance_split | id、amount（元，少于整笔；0 合回去）、category；把一笔支出里用户自己的那部分拆成单独一笔 |
| finance_balance | 空对象列出各账户余额；account、amount（元，可为 0）、at?（YYYY-MM-DD，默认今天）记下余额；account、remove=true 忘掉一个账户 |
| finance_reread | 无参数；用现在的读取规则把归档的账单再读一遍，只补上以前漏掉的交易，已有的交易和用户的决定不变；归档的是 zip 时需要密码，跳过 |
| finance_home | start、end（YYYY-MM-DD）、remove?；记下或拿掉一段在家的日子，返回全部 |
| finance_unlock | file（最外层 ZIP 文件名）、password；只用一次，不复述密码 |
| finance_import_now | 空对象，立即扫描 |
| finance_report_input | start（周期起始 YYYY-MM-DD），汇总快照、上期比较，无商户或对方 |
| finance_report_write | start、text（1–4000 字），只写本周期解读 |

## 卡片和每日文件

卡片在 `plugins/finance/cards.py`，数字全由代码算，不经过模型。顺序：

- `stat`「10月还能花」（标题是这个周期开始的月份；first=true、wide=true）：value 是剩下的整数元（可为负），label 第一行「已花 1,161 / 2,000 元 · 还有 3 天，每天约 280 元」（超了不写每天），第二行账单截至哪天（这个月一张都还没导入时写「10月的账单还没导入，导入后这里会更新」，有来源还没导入时写各来源的截至日期），生活费没到账时再加一行按设置金额算。`bar`：`max` 是预算，`segments` 是各类别（同下面圆环的顺序和颜色），超了 `tone: alert`，照现在的速度月底会超时 `tone: warn`。
- `text`「记账的建议」：`headline` 一句话，`text` 两三行「- 」，`symbol` 随情况换。账单已覆盖本周期至少 5 天时按节奏推算月底：已经超了（`takeoutbag…`）写外卖几次多少钱、剩下几天去食堂，以及花得最多的类别和怎么省；推算会超生活费的二十分之一以上时写每天控制在多少以内和外卖；推算剩下生活费的一成以上（至少 200 元）时（`gift.fill`）建议拿剩下的一半（按 50 元取整）买点喜欢的东西犒劳自己，其余留着；其余（`checkmark.seal.fill`）说节奏刚好。不到 5 天时看上个周期：剩了多少（同样建议犒劳）、超了多少（外卖、花得最多的类别），再给这个月每天约多少。一张账单都没有时说怎么导入。只谈花钱习惯，不提任何金融产品。
- `chart kind=donut`「10月钱花在哪儿」：这个周期还没有花销时画上个周期。`value` 是整数元，`points` 只有有钱的类别、从多到少，每段 `label`「344 元」；`label` 是起止日期，有外卖时加「外卖 9 次 245 元」。
- `chart kind=bar`「每月花销」：最近六个周期里账单全部覆盖的那些（每个来源最早导入的日期之后开始的周期），`points` 的 `label` 是整数元，`target` 是这个周期的预算（「生活费 2,000」）。少于两个周期时不显示。
- `stat`「现有资产」、`stat`「今年额外收入」（整数元，label 只写有的红包、分红等）、`list`「今年的大件」。
- `list`「账单」：各来源截至日期、需要密码、无法识别、重复归档文件；有在家时的花销时一行合计（不逐笔列出）、家里报销（yes 和 reimbursed 的合计，不逐笔列出）、家里转来和未知转入提示。

用到的 `wide`、`bar`、`target` 和点的 `label` 是通用的卡片字段，见 [api.md](api.md)。

当天有导入或手动记账才生成每日 `记账.md`，Bot 为「记账Bot」，只写当天**新增入账**的条数、支出和转入总额，历史账单按导入日统计，明确不代表当天消费。每日目录所有 Bot 都能读，不写商户、原文、单号或账单路径。

## 月报

`monthly_report` 默认每天 09:00 检查上一个生活费周期：已结束、尚未写完，且三个来源完整覆盖周期，或已到新生活费日后第 4 天（默认 5 日），开始生成。仍无账单时也按兜底日期生成，并明确全部来源未导入，不能据此判断实际花销。代码先写预算、花销、分类与上周期比较、报销、额外收入、覆盖及本地最大的几笔到 `月报/<周期开始 YYYY-MM>.md`；同名已有文件加后缀，绝不覆盖。

随后 `context.run_agent` 按 `prompts/finance_report.md` 启动汇总身份的 Agent，先调 `finance_report_input`，再调 `finance_report_write`。数字快照不会包含最大几笔或任何商户/对方；解读追加到「## 记账的话」并写 App 摘要。文件被用户改过时拒绝追加。Agent 失败保留数字部分、runs 记固定失败分类，下次检查可重试。月报解读按固定的三节写：**花在哪**（花了多少、和上个周期比、主要类别和外卖）、**余额**（剩多少或超多少、大件、额外收入、数据缺口）、**建议**（剩得多就建议拿一部分买点喜欢的东西，超了就少点外卖、看看不用的会员，和卡片「记账的建议」同一套规则）；每行不超过 30 字，全文不超过 300 字。只谈花钱习惯，不给投资理财借贷建议。

## 配置

配置 schema 不接受无关字段，ZIP 密码和任何账户密码都不是配置项。

| topic | 财务 | 私人知识库主题 |
| cron | `*/5 * * * *` | 收件箱扫描 |
| reimburse_cron | `0 21 * * sun` | 报销确认提醒 |
| report_cron | `0 9 * * *` | 检查上期月报 |
| allowance_day | 1 | 1–31，短月自动取末日 |
| allowance_amount | 2000 | 元，未识别生活费时的周期预算 |
| family | [] | 生活费对方包含匹配名单，空则不限制 |
| family_pays | [] | 家里报销的支出：对方或商品包含其中一个关键词（不分大小写），不进生活费 |
| extra_income_keywords | [分红] | 转入的对方或商品/摘要包含匹配 |
| sources | wechat、alipay、cmb | 用户在用的来源；卡片只列这些（另加已有数据的），月报只等这些来源的账单覆盖完整。支付宝走银行卡、没有余额的，银行流水里已经有这些支付，可以不列 alipay |

## 隐私边界与验证限制

账单原件、临时解压文件、PDF 提取缓存、SQLite 账本及本地月报均在用户机器。其他 Bot 的财务工具只能看汇总；MCP 读文件仍依赖主题 ACL。MAIN、旧无 reader 令牌和拥有终端权限的本机程序是现有兼容例外，不是操作系统隔离。App 用户本人能看明细和带明细的报销摘要。

记账对话照常保存，这样 App 里能看到自己说过的话，她也记得前面聊了什么。Agent 用 `finance_unlock` 解锁压缩包时，用到的密码会从**这一轮**你说的那句里换成「（密码已隐藏）」（`messages` 和 `chat_messages` 都改），也从她的回复里遮掉；之后的对话历史里不再有它。没有经过 `finance_unlock` 的话不会被改动，所以密码只在解锁时说。当前这句仍交给你选的 Agent，密码因此会经过该模型供应方；Agent CLI/模型服务自身的会话留存不由本插件保证。若不希望密码经过模型，请自己解压后上传。对话回复、财务摘要和本地报表可含金额，但日志、runs、错误不含金额、商户或转账对象。

**本轮只用编造账单验证，不能当成三家真实格式已兼容。** 特别是以下假设需要真实脱敏样本再核对：

- 微信：CSV 前置说明行数量不固定，按表头查找；只支持列名别名范围内的变体。「已退款 / 已全额退款」假定原支出已全部退回；未明确给出金额的部分退款不能推断。
- 支付宝：假定 UTF-8 或 GB18030（含常见 GBK）、个人对账的所列列名、交易关闭不入账；其他“证明”“余额明细”结构不猜。未验证当前导出菜单及不同版本状态文案。
- XLSX：只读第一张工作表，sharedStrings / inlineStr / 缓存值，默认 1900 日期系统；1904 日期系统拒绝。若平台把长订单号存为 Excel 数字而已损失精度，插件不能还原。
- 招商银行：**版式是按题目假定的六列文本**；日期须含年、人民币金额/余额须两位小数、每笔在同一行且摘要/对手能分成两列，跳过非日期页眉页脚。跨行、列错位、外币或扫描后 OCR 错误会拒绝整份。测试只给 FakeExtractor 编造的 doc-text pages，未运行真实 PDFKit/Vision。
- 覆盖期间仅识别起始/终止、开始/结束、起止日期、账单/交易/查询期间等标记；识别不到只用交易最早/最晚日期并显示不完整覆盖，不以文件名补猜。多候选去重、仅凭日期和金额的生活费/报销识别需要用户核对。
- 真实平台 ZIP 加密方式、PDF 文本布局、真模型月报与 App 真机展示均未验收；AES 需要用户解压。测试不联网，不绑定端口，不读真实账单或账户。
